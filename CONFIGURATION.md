# Configuration model

Every configurable concern has an explicit default chosen by the user. Optional overrides replace that default for a particular target. A default is a configuration value, not another runtime state or a recovery mode.

An absent override uses the configured default. An invalid value reports an error. A missing required default reports an error too; the system never invents a wallpaper, monitor, theme, or policy to conceal incomplete configuration.

Defaults live with the concern they control. There is no additional configuration service or universal settings layer. Lua configures Hyprland; QML configures the shell; focused scripts render and persist their generated values.

## Hyprland target

The Hyprland configuration targets version 0.57.0 or newer, with no compatibility path for older versions. Scrolling uses the explicit integer `follow_focus = 1`; group locking uses `hl.dsp.group.lock({ action = "toggle" })`. Layer policy allows newly opened Quickshell overlays above fullscreen windows and preserves keyboard focus when the pointer moves.

## Installation manifest

The installed package lives at `$XDG_CONFIG_HOME/ui-shell/` (or `$HOME/.config/ui-shell/` when `XDG_CONFIG_HOME` is unset), with `scripts/`, `quickshell/`, `themes/`, `profiles/`, `default/`, `hypr/`, and `config.ini`. The source tree separates runtime `scripts/`, `shell/`, `hypr/`, and the single `default/` seed; staging maps those source directories into the installed layout and creates the runtime stores. Development staging is implemented by `tools/scripts/stage-config`; test checks and helpers live in `tests/scripts/` and are not installed. `config.ini` is a strict, versioned installation/path and theme-source manifest, not behavior or UI configuration. QML owns shell behavior and style; Lua owns Hyprland policy.

The source seed of the manifest is `tools/config.ini` (checkout development and tests only); staging and the test runner copy it to the installed `config.ini` once and never overwrite an existing one. Manifest schema 2 paths resolve relative to the directory containing `config.ini`. Only a leading literal `${HOME}`, `${XDG_CONFIG_HOME}`, `${XDG_CACHE_HOME}`, `${XDG_DATA_HOME}`, or `${XDG_STATE_HOME}` is recognized; values are never evaluated as shell code. The reader rejects unknown/missing schema fields and unsafe or unresolved paths. Bootstrap passes explicit absolute arguments to `read-shell-config` (`config.ini` and `scripts/read-ini`); it then passes the resolved JSON file path to `prepare-runtime`. After resolution, command-role values are absolute and consumers invoke `.commands.<role>` rather than rebuilding checkout paths. `[wallpaper_folders]` owns the complete wallpaper directory list. Source-tree paths such as `shell/` and `hypr/` describe development inputs; production runtime addresses come from the resolved manifest. The standard cache outputs are `${XDG_CACHE_HOME}/ui-shell/runtime/config.json` and `config.lua`; Bash receives the JSON path through `UI_SHELL_RUNTIME`, while QML and Lua consume native generated modules. The three `[bootstrap]` entries configure the runtime QML path, wallpaper-catalog QML path, and `profileModule` link location inside the configured Quickshell root. `prepare-runtime` atomically links `profileModule` to the compiled bundle's `quickshell/` directory; compiled files remain in XDG cache. `GeneratedRuntime.qml` imports the configured module by a relative path inside the Quickshell root, avoiding imports that escape the root. Consumers use the generated runtime/module contract and configured helper roles, not hardcoded generated filenames. JSON is an intermediate, not user or QML configuration.

`make dev-stage` and `make dev-configure` use the checkout-private `.build/home/.config/ui-shell` package; they do not install into the host configuration directory.

`config.ini` selects the profile recipe used at startup through `[theme] profile`. A reusable Theme definition is a colors-only schema-2 `config.ini`: `[palette]` declares mode and explicit shell roles, `[colors]` retains every named palette slot, and `[hyprland]` retains native border expressions, including gradient stops, opacity and angle. The shipped default is generated from `default/default.png` into `default/theme.ini` and `default/profile.ini`; staging installs it as `themes/default/config.ini` and `profiles/default/profile.ini` only when those stores are absent. Authored definitions use `themes/<name>/config.ini`, discovered under configured `[paths] themes`. `[paths] profiles` is `profiles`. Each schema-2 recipe contains complete durable color snapshots, wallpaper choices, optional named Theme identity, and scoped overrides. It has no `objects/`, `versions/`, or wallpaper-registry sidecar. Themes do not define wallpaper, behavior, shape, density, typography, or motion. See [the Theme contract](docs/themes.md) and [the palette format](shell/theme/README.md).

Profile recipes are durable inputs in XDG config; complete compiled generations are derived in `${XDG_CACHE_HOME}/ui-shell/profiles/<id>/<build-key>/`. A generation contains `global.json`, `palettes/default.json` and hashed per-output palette files, `state.json`, `wallpapers.json`, `wallpapers.lua`, `quickshell/{GeneratedPalette.qml,GeneratedPalettes.qml,WallpaperTargets.qml,qmldir}`, `hyprland/colors.lua` and hashed output Lua files, `hyprpaper/hyprpaper.conf`, and `checksums.sha256`. The build key covers recipe bytes, selected inputs, configured runtime inputs, and renderer/helper bytes. A checksum-valid cache hit is reused; missing or invalid generations are rebuilt from durable inputs. `[paths] profileCache` configures this cache root. `[bootstrap] runtime`, `wallpaperCatalog`, and `profileModule` are installation metadata: only the last is a configured link point into Quickshell, atomically linked to the compiled generation's `quickshell/` directory by `prepare-runtime`. The QML runtime imports through this in-root module link; generated profile files remain in cache. Required native targets are Quickshell, Hyprland, and Hyprpaper; optional GTK/Qt renderers use the same `INPUTS_JSON OUTPUT_DIRECTORY` helper contract. All targets render in staging before atomic generation publication and profile selection. There is no schema-1 compatibility, legacy migration, or silent conversion/deletion.

The Theme catalog uses a fast Python metadata scan of Theme `config.ini` files only. Listing reads metadata; it does not validate every palette or profile. Selecting a Theme reads and validates only its palette. Wallpaper and profile validation occur as needed for the chosen operation and at final apply. An invalid selection shows the scoped popup and preserves the prior draft. The native dropdown is virtualized and inactive while closed; `shell/theme/Density.qml` explicitly defines its maximum height and viewport margin. Profiles retain the selected Theme's config-root-relative `definition` and per-output `[definition_overrides]`, so source labels survive restart without rereading Theme colors. File Themes load their owned committed palettes; wallpaper colors are extracted only when needed and reused from the content-addressed XDG cache.

Enter, Choose theme or Ctrl+T in the wallpaper picker advances the chosen image to palette choice without changing the desktop. Choosing a Theme reads its palette into the draft; choosing Wallpaper derives colors from the chosen image. Mode is metadata and does not invert colors. Only Save and apply creates or updates a committed profile and activates the wallpaper/palette together; Ctrl+Enter invokes that action unless a nested popup owns focus. Back preserves the draft; closing the picker discards it. The picker-captured target remains internal, without an inline monitor label. No editor scrolling is needed in the default 1280×720 test viewport. Height follows visible content plus normal padding, capped by the configured maximum and runtime viewport, without stretched rows or unused footer space. Defaults and geometry are explicit in `shell/config/ThemeEditor.qml`.

Wallpaper-derived colors retain each image's own content-addressed Matugen palette. Theme definitions contain palette colors only. A committed profile records the palette and wallpaper choices made together at Save and apply. Configuration choices and initial focus use stable named identities; list order never determines a source, mode, scope or RGB channel. Numeric indexes are limited to explicit runtime-index configuration, iteration, framework events and bounds checks.

## Wallpaper

All wallpaper folders are user-owned entries in `config.ini`, never directory constants in the picker or scripts:

```ini
[wallpaper_folders]
default = default
project = wallpapers
personal = ${HOME}/Pictures/Wallpapers
```

Enable only folders that exist and are readable. Folder IDs contain letters, digits, underscores or hyphens and stay stable when their directory moves. Paths use the manifest rules above; the relative `default` and `wallpapers` entries are checked-in choices, not built-in locations. The catalog lists JPEG, PNG and WebP files directly inside every configured folder, without recursive scanning. Duplicate filenames in different folders remain separate candidates; search includes the folder ID and Ctrl+I identifies it. Missing folders and unknown IDs fail explicitly instead of silently omitting a source or selecting another one.

The recipe's `[wallpaper.default]` selection and optional `[wallpaper.<scope>]` sections persist wallpaper choices directly alongside colors and policy. Each selection names its folder ID, filename, fit mode, and generated palette key. The picker lists images from all configured folders together and keeps edits in the draft until Save and apply; the XDG cache holds derived colors and compiled projections, while the recipe remains the durable choice. Moving a folder requires changing only its manifest path and regenerating the runtime; saved selections retain their IDs. Missing or unknown folder IDs are errors; no folder is inferred.

A display without an override uses `default`. A new display works immediately with that same user-set value. Creating a display override starts with the default fit mode. Removing its recipe override returns it to the default on the next session startup.

The picker's **Shared default** target edits this baseline. A named display target edits that display's override. The chosen target remains visible in the picker and is retained internally by the editor; further information is available through Ctrl+I. Updating the shared default affects displays that inherit it; existing display overrides remain explicit choices. Choose theme prepares the draft image's cached colors without persisting or applying its selection. Save and apply validates and publishes the wallpaper and palette association before native activation. Wallpaper-derived colors follow each image; a selected Theme supplies its declared palette. Other wallpaper selections and palette scopes remain unchanged until commit.

“In use” is the only tile status marker and means the last confirmed native wallpaper. The candidate outline indicates which image Enter will take to the next step. The persisted choice determines the opening candidate. Shared default is an output scope, not a runtime state. The selected recipe supplies startup choices; the reusable default Theme remains an independent colors-only definition.

Hyprpaper represents its native default target with an empty output string. That string is a transport detail in generated target data and script arguments; the user-facing name and Lua setting are Shared default and `default`.

The manifest remains schema 2 and has no `[wallpaper]` section or `defaultFolder`; `[wallpaper_folders]` is its only wallpaper configuration. The default wallpaper remains the user's configured baseline, and per-monitor entries remain optional overrides.

## Colors and style

The prepared profile bundle's `GeneratedPalettes.qml` supplies one required `defaultPalette` and a `byOutput` map at startup. `ActivePalettes.qml` owns the running values; `forOutput(name)` resolves the explicit override or that configured default. Successful profile activation loads the prepared native QML values. Palette-dependent image caches use `${XDG_CACHE_HOME}/ui-shell`; complete profile generations use the configured `profileCache`. There is no separate policy for displays without an assignment and no JSON configuration reader in the UI. The native bootstrap imports the generated bundle; it does not make JSON user configuration.

`hypr/user/monitors.lua` chooses the compositor/global palette source explicitly in wallpaper mode. `palette_source.kind = "default-wallpaper"` uses the default wallpaper's colors; `"output-wallpaper"` chooses one configured display override and requires its exact output name. The selected recipe supplies palette data for the global palette. QML output palettes are independent; this does not create per-monitor Hyprland border settings. Startup prepares the complete selected generation before the Hyprland UI starts.

`shell/config/*.qml` and `shell/theme/{Shape,Density,Typography,Motion,Interaction}.qml` contain the shell's user-editable baseline options and style values. Components receive those values through composition. An override can replace only its declared concern; it does not introduce unrelated behavior or a new state.

Each owning style derives a `ControlColors` instance from its palette. `ControlState.colors` consumes those typed roles, keeping color sources separate from interaction flags. `Interaction.qml` exposes the foreground/outline mixes, 4.5:1 text and 3:1 boundary contrast floors, tonal endpoints, and committed-marker size. Dropdown rows are explicitly borderless in all states: hover/candidate foregrounds and a compact committed-choice marker identify options inside the popup's single border. Dropdown, runner and wallpaper item labels always use the configured `Typography.bodyWeight`; interaction never changes font weight.

`tools/scripts/import-reference-themes` converts local `refs/100-themes` color definitions into Theme `config.ini` files under resolved `paths.themes`. Positive, warning, and negative source fields are explicit choices, not inferred from ANSI names. It validates the discovered set before publishing and overwrites only matching flat reference Theme IDs; unrelated/custom Theme IDs and all profile recipes remain untouched. `dev-import-themes` stages and resolves configuration without preparing runtime or compiling profiles. Nested `test-import-themes` exits before runtime preparation, so neither path generates profile cache/bundle data. The wrapper and converter accept only their documented five- and seven-argument interfaces; no legacy compatibility is provided. Opening and canceling creates no profile either. Final Save and apply persists recipe inputs, prepares the complete native generation, and activates it once. The persist-only helper saves validated inputs without rebuilding native outputs; activation compiles the selected recipe before native application. See [the palette API and offline workflow](shell/theme/README.md).

`shell/config/Config.qml` explicitly sets `watchSourceFiles: false`. Generated QML is loaded through revision-qualified native data loaders, not a whole-shell source reload that would discard in-flight drafts. Enable source watching only deliberately for development; that permits normal Quickshell source reloads. Palette/profile operations need no custom IPC or daemon.

## Monitor configuration

`hypr/user/monitors.lua` contains `default` monitor settings and an `overrides` list. Named overrides compose over that default; omitted fields retain its explicit values. Output discovery is runtime data, so the shipped default has `overrides = {}` and never contains a guessed hardware name. Staging preserves the user-owned `monitors.lua` while refreshing every other runtime file. `tools/scripts/generate-monitor-overrides` prints an explicit override table for the current session so it can be reviewed and merged; host-specific output is never committed as a default.

Picker hosting is a separate user choice in `shell/config/Outputs.qml`. An unavailable explicitly selected screen is an error; choosing a default wallpaper does not select a different host screen.

## Launcher output and icons

Launcher host defaults live in `shell/config/Outputs.qml`: `launcherDefaultTargetMode`, `launcherDefaultScreenIndex`, and `launcherDefaultOutputName`. The checked-in default explicitly selects runtime screen index zero without naming hardware. `screen-index` chooses exactly that zero-based index; `output-name` chooses exactly the user-supplied name. Invalid modes or unavailable targets report errors, never substitute another screen.

`shell/config/GeneratedLauncherOutput.qml` is an optional generated override. Its undefined fields retain the declared user defaults; it is not another runtime state. Prefer generating machine-specific choices instead of embedding them in components:

```sh
bash scripts/render-shell-launcher-output shell/config/GeneratedLauncherOutput.qml screen-index 1
# Or choose an exact name supplied by the user:
bash scripts/render-shell-launcher-output shell/config/GeneratedLauncherOutput.qml output-name '<output name>'
```

The renderer replaces only this output policy atomically; malformed input leaves the previous file unchanged. Restart Quickshell to load a regenerated policy. Clear override fields to `undefined` to return to the explicit defaults. Host selection is independent of per-output palettes, wallpapers, and Hyprland monitor geometry.

`shell/config/AppLauncher.qml` owns launcher behavior. `showIcons: false` removes icon space and image requests; `true` uses the explicitly configured icon size and `defaultIcon`. Theme resolution belongs to Qt/`QS_ICON_THEME`, not guessed icon paths or device-specific component logic. Search fields, excluded desktop-entry IDs, app2unit arguments, and lazy loading/retention are likewise explicit QML options.

## Component-scoped settings

Ctrl+E opens settings for the active component and the explicitly shown scope. Ctrl+I shows contextual information; Ctrl+Space shows that component's usage and configured keys. The minimal launcher and picker have no redundant headings, permanent help, inline descriptions, or large Close buttons.

The initial editable keys are launcher `showIcons` and `visibleRows`, and wallpaper `wideColumns` and `maximumVisibleRows`. Static QML configuration supplies defaults. Generated QML overrides are stored under `${XDG_CONFIG_HOME}/ui-shell/components/{launcher,wallpaper}/`: `Default.qml` holds shared choices, and `outputs/<sha256 of exact UTF-8 output name>.qml` holds an exact-output override. Undefined properties inherit the lower-priority value. The settings scope is the output hosting the UI; for wallpaper settings it is independent of the picker’s destination selector.

Settings edits are drafts. Only Save writes. Per-file locks and revision compare-and-swap reject stale edits; validated files are atomically replaced. A successful save reloads the QML override live. Opening settings refreshes it from disk. These are small separate Bash scripts around native QML configuration: there is no watcher, IPC, daemon, or JSON shell configuration.

User choices live in XDG configuration storage, not the cache for derived palettes/assets. The package and component settings use the `ui-shell` configuration namespace. Wallpaper color cache defaults to `${XDG_CACHE_HOME}/ui-shell/wallpapers`; durable wallpaper selections live in `profiles/<id>/profile.ini`. The generated Hyprpaper configuration is exposed as `bundle.hyprpaper` and resides in the compiled profile generation under `${XDG_CACHE_HOME}/ui-shell/profiles/<id>/<build-key>/hyprpaper/hyprpaper.conf`. Runtime paths remain in the `ui-shell` namespace. Invalid values, write failures, and edit conflicts report errors while preserving the last valid configuration. See [STYLE.md](STYLE.md) for popup focus, dismissal, and border behavior.

## Notifications

The shell is the only notification daemon (`shell/config/Notifications.qml` holds timeouts, sound and spoiler settings). Rules are a hand-written `property var rules` list in `${XDG_CONFIG_HOME}/ui-shell/components/notifications/Default.qml`, for example `[{ name: "x", app: "notify-send", mute: true }]`; fields `app` and `appId` (exact), `appMatch` (a case-insensitive regular expression over the app name), `match` (one over the summary and body), `hide`, `mute`, `reveal`, `sound`. `reveal: true` exempts matching notifications from the recording blur (use it only for apps whose text is safe to show on a recording). A rule changes presentation only and leaves a "rule: name" tag in the drawer. The file is read once, when the shell starts (restart the shell to apply an edit; there is no watcher); an invalid rule keeps the last good set and shows one error. Sound is off by default (`soundEnabled`, `soundFile`) and plays through `scripts/notify-sound` (`pw-play`). While recording, message text is covered by an animated spoiler shader (`make dev-shaders` rebuilds `shell/modules/notifications/shaders/spoiler.frag.qsb`). Nested sessions bind the drawer and DND to F6/F7 through `shell_shortcut_keys`.

## Error presentation

The shared `ErrorPopup.qml` receives the failed operation, message, exact target/scope and diagnostic details from its owning component. Backend failure signals present one popup per new failure; dismissal does not reopen that failure. The diagnostic details are read-only, selectable and scrollable plain text. Explicit Copy includes the title, message and all details through native Qt text-control copying without clipboard utilities or automatic clipboard writes. Escape, outside-click and dismissal restore interrupted focus while preserving current selection and settings drafts. A scoped settings error appears above the editor. Static `config/ErrorPanels.qml` controls popup width, diagnostic height, padding, keys and initial focus; its defaults are Dismiss focus, Escape dismissal and Ctrl+Shift+C full Copy. Tab and Shift+Tab cycle only Dismiss/Copy; diagnostics can be pointer/explicitly focused for native text copying, then Tab leaves them. Details scrolling controls do not take focus, and initial focus may be Dismiss or Copy, never details. Shared popup spacing/scrim and motion remain in `ContextPanels.qml` and `theme/Motion.qml`. See [STYLE.md](STYLE.md).

## Applying the rule to future features

Define the default in the owning configuration file before adding optional overrides. Resolve overrides against it at the composition boundary, then pass concrete values to the component. Document what an override changes. Keep loading, selection, focus, and operation errors as runtime states; configuration defaults stay configuration values.

## Private test preferences

`tests/nested.conf` declares test-state policy and its dedicated storage directory. Every run stages fresh code at the private `$XDG_CONFIG_HOME/ui-shell`; production consumers use that installed package, not `/project` addresses. `make test-env` and `make test-env-persistent` retain the same private home/cache, manifest, Theme definitions, current-schema profile recipes, scoped settings and wallpaper selections across runs. Main preserves current-schema choices. `make test-import-themes` refreshes matching reference Theme IDs while leaving unrelated/custom Theme IDs and all profile recipes untouched. Older private unreleased choices require `make test-env-clean`, which preserves imported Theme definitions. Reference root and semantic status fields are declared in `tests/nested.conf`, separately from read-only sandbox exposure. Close an active persistent session before importing. `make test-env-fresh` starts an explicitly ephemeral interactive session; `make test-env-snapshot` captures a bounded session and exits while retaining private preferences. `make test-env-phantomat` opens a disposable plugin session, waits after compositor readiness, and depends on `make dev-build-phantomat`. All automated GUI checks use ephemeral state. Test folder exposure is separately declared in `tests/nested.conf`; adding a folder to the manifest does not grant sandbox access to arbitrary host directories. See [tests/README.md](tests/README.md) for the mounts and lifecycle.
